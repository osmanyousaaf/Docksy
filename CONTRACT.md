# Docksy build contract

Single source of truth for the parallel build. **If code and this file disagree, this file wins.** Need a change? Do not edit this file — say so in your final report.

## 1. Product

Docksy is a free-forever, open-source, self-hosted PaaS (a simpler Coolify) with three wedges:

1. **Monitoring on by default.** Live CPU, memory, disk and network for every server and container, plus alerts, uptime checks and a status page, all working out of the box.
2. **AI-native.** A first-party MCP server, a Claude Code plugin and skills. Claude can deploy, read metrics, diagnose and fix problems. Docksy itself never calls an LLM: diagnose is deterministic and Claude does the reasoning.
3. **Simple, reliable deploys.** Push to GitHub and it deploys with zero downtime. Rollback, one-click databases and backups with restore verification.

Distribution is GitHub only (`github.com/osmanyousaaf/docksy`), plus npm under `@crovenai/*` and images on GHCR (`ghcr.io/osmanyousaaf/docksy`). There are no paid tiers, no telemetry and no phoning home.

## 3. Stack and commands

- **Node 24.** The server runs TypeScript directly with Node's type stripping (`node src/index.ts`):
  - no build step and no `enum`/`namespace`/parameter properties (`erasableSyntaxOnly`)
  - relative imports **must** end in `.ts`
  - import shared types with `import type { … } from '@docksy/shared'` (types only, never runtime values)
- **Database:** `node:sqlite` (`DatabaseSync`, synchronous), schema in `apps/server/src/db/schema.sql`.
- **HTTP:** Hono 4 + `@hono/node-server`. Validation uses zod 4 (`import { z } from 'zod'`). Streaming uses SSE (`import { streamSSE } from 'hono/streaming'`).
- **Server dependencies available:** `hono`, `@hono/node-server`, `zod`, `ssh2`, `nodemailer`.
- **Web:** React 19, Vite 8, Tailwind 4 (tokens in `src/index.css`: `bg-bg`, `bg-surface`, `bg-surface-2`, `border-border`, `text-fg`, `text-muted`, `text-brand`, `text-brand-2`, `text-ok`, `text-warn`, `text-bad`, `--color-cpu`/`mem`/`disk`/`net-rx`/`net-tx`), react-router 8 (`import { Link, useParams, useNavigate } from 'react-router'`), TanStack Query 5, recharts 3, lucide-react, clsx.

- **Go agent:** Go is not installed on this Mac. Build and test inside Docker:
  `docker run --rm -v "$PWD/agent":/src -v docksy-gomod:/go/pkg/mod -w /src golang:1.24 go test ./...`
- **Tests:** `node --test` with `*.test.ts` files next to the code. Import `node:test` and `node:assert/strict`. Server tests set `DOCKSY_DB_PATH=:memory:` (or a temp file) and `DOCKSY_DISABLE_JOBS=1` **before** importing `db`, then call `migrate()`.
- **Verify commands** (run from repo root `docksy/`):
  - `npm run typecheck -w @docksy/server`

## 4. HTTP API (base `/api/v1`, JSON, types in `packages/shared/src/index.ts`)

**Conventions**
- **Auth:** session cookie `docksy_session` or `Authorization: Bearer dsk_…`. Use `requireUser` from `lib/auth.ts` on every non-public route.
- **Errors:** throw `HttpError` (or `notFound()` / `badRequest()` / `conflict()`). The server returns `ApiError` JSON for them.
- **Writes:** log an activity entry on every write with `logActivity(c.get('actor'), 'app.deploy', 'app', id)`.
- **List responses:** `{ items: T[] }`, plus `total` when paginated.
- **Responses:** the created/updated entity itself, or `{ ok: true }`.
- **Request IDs:** routes taking `:id` for apps accept the app's id or its name.

Export `enqueueDeployment(appId, trigger, meta?) => Deployment` from `core/deploy/queue.ts`; `core-apps` imports it.

The queue runs one deployment at a time per app and up to 3 concurrently overall. Pipeline (all over SSH):

1. Clone with `git clone --depth 1 -b <branch>`; use `https://x-access-token:<token>@…` when the app has a git token.
2. Record the commit sha and message.
3. Build:
   - `dockerfile`: `docker build -f <dockerfilePath> <context>`
   - `auto`: use the Dockerfile if present, otherwise generate one from built-in templates detecting Node (package.json), Python (requirements.txt/pyproject), Go (go.mod), static (index.html)
   - `compose`: `docker compose -p docksy-<name> up -d --build`
   - `image`: `docker pull`
4. Tag the image `docksy/<name>:<deploymentShort>`.
5. Start the new container with:
   - env from `getAppEnv`
   - labels: §6 plus Caddy labels
   - network `docksy`
   - volumes
   - `--restart unless-stopped`
6. Wait for health: `healthcheckPath` via `docker exec` + wget/curl, or until the container is running for 5s. Timeout 120s.
7. Remove the old containers for this app. This is **zero-downtime**: the old container stays until the new one is healthy. On failure the new container is removed and the old one stays.
8. Mark the deployment succeeded or failed. Set the app status and `current_deployment_id`. Emit `deployment.status`, `deployment.log` and `deployment.finished`.
9. Prune old build dirs; keep the last 5 images per app.

At startup, seed default global rules if none exist (`is_default=1`):

| Rule | Threshold | Severity |
|---|---|---|
| CPU | > 90% for 5m | warning |
| Memory | > 90% for 5m | critical |
| Disk | > 85% | warning |
| Disk | > 95% | critical |
| Server offline | 2m | critical |
| Container down (managed container not running) | — | critical |
| Container restarts | > 3 in 10m | warning |
| Deploy failed | — | warning |
| Uptime down | — | critical |
| Backup failed | — | critical |

How alerts work:
- **Evaluation.** Metric rules are checked on each `server.report`, using the recent raw window for durations. A loop every 30s handles offline detection. Event rules are triggered from bus events.
- **One firing alert per dedupe_key.** An alert is resolved automatically when its condition clears.
- **Notifications.** On fire and on resolve, send to the rule's channels via `notify.ts`:
  - Discord, Slack and generic webhook use `fetch`
  - Telegram uses the Bot API
  - email uses nodemailer
- Alert messages are short and human, and end with a hint: "Ask Claude: `/docksy:diagnose <server>`".
- Emit `alert.fired` and `alert.resolved`.
- Export `fireEventAlert(metric, {serverId?, appId?, title, message, severity?, value?, key})` and `resolveEventAlert(key)` from `monitoring/alerts/engine.ts`. Other modules import these (mon-uptime, mon-backups).

**`mon-uptime`: uptime + status page + diagnose**

| Method | Path | Notes |
|---|---|---|
| GET POST | `/uptime-checks` | |
| PATCH DELETE | `/uptime-checks/:id` | |
| GET | `/uptime-checks/:id/results?range=24h` | |
| GET | `/public/status` | **public**; 404 unless `settings.statusPageEnabled` → `PublicStatus` |
| GET | `/diagnose?serverId=&appId=` | → `DiagnoseReport` |

- **Uptime checks:** a scheduler runs each check at its interval with `fetch` + AbortSignal.timeout, keeping 90 days of results. When a check flips down, call `fireEventAlert('uptime_down', …)`; when it comes back up, call `resolveEventAlert`.
- **Auto-check:** when an app gets a domain (listen for `deployment.finished` succeeded), auto-create a check for `https://<primary domain>` if none exists.
- **Diagnose** is rule-based. Its findings cover:
  - high CPU or memory, plus the top containers by usage
  - disk nearly full, with docker prune suggestions
  - swap thrashing
  - offline agent
  - container restart loops or OOM-kills (inspect `docker inspect` State.OOMKilled via ssh)
  - a failed last deployment, with its error and the tail of the build log
  - recent errors in app logs (regex `error|exception|fatal|panic|killed`)
  - expired or missing TLS on the domain
  - unhealthy uptime checks
  Each finding fills `suggestion` and, when possible, `action` with an MCP tool name from §8.

**`mon-backups`**

| Method | Path | Notes |
|---|---|---|
| GET POST | `/backups?appId=` | |
| PATCH DELETE | `/backups/:id` | |
| POST | `/backups/:id/run` | → `BackupRun` |
| GET | `/backups/:id/runs` | |
| POST | `/backup-runs/:id/verify` | |
| POST | `/backup-runs/:id/restore` | requires body `{confirm: true}` |

- **Supported templates:** postgres (`pg_dumpall`), mysql/mariadb (`mysqldump --all-databases`), mongodb (`mongodump --archive`), redis (`BGSAVE` + copy `dump.rdb`).
- **Each run:**
  1. Dump inside the container: `docker exec … | gzip > /var/lib/docksy/backups/<app>/<ts>.gz`.
  2. Optionally upload to S3-compatible storage. Sign requests with SigV4 yourself in `s3.ts` (node:crypto), or use `aws`/`mc`/`rclone` on the server if present.
  3. Prune to the retention count.
- **Verify:** start a throwaway container of the same image on the server, restore the dump, run a sanity query (`SELECT 1` / count of databases, `db.stats()`, `DBSIZE`), then remove the container. Set `verified`.
- **Scheduler:** hourly, daily or weekly, checked every minute. On failure call `fireEventAlert('backup_failed', …)`.

### 4.3 Agent protocol (`go-agent` ↔ `mon-metrics`)

- **Sending:** every `DOCKSY_AGENT_INTERVAL` seconds (default 10), POST `${DOCKSY_URL}/api/agent/v1/report` with `Authorization: Bearer ${DOCKSY_AGENT_TOKEN}`. The body is `AgentReport` JSON (exact field names in shared types).
- **Retries:** use the `intervalSec` from the response. On failure, back off up to 60s and keep only the latest report (no unbounded buffering).
- **CPU percent** comes from /proc/stat deltas. Memory "used" = total − available. Disks are real filesystems only (skip tmpfs/overlay/squashfs). Net is the sum across non-loopback, non-veth/docker/br- interfaces, as a bytes/s delta.
- **Containers** are read from the Docker Engine API over `/var/run/docker.sock`:
  - `/containers/json?all=1` for the list
  - one-shot `/containers/{id}/stats?stream=false` for running containers, fetched concurrently with a 3s timeout each
  - `RestartCount` from inspect
  - CPU% calculated the docker way; mem used = usage − inactive_file
- **Constraints:**
  - Must run unprivileged except for read access to the docker socket.
  - Static binary, `CGO_ENABLED=0`.
  - Go standard library only (no gopsutil); read /proc directly.
  - Under 15 MB RSS and under 1% CPU.

## 6. Server-side conventions (on each VPS)

- **Docker network:** `docksy`.
- **Proxy:** container `docksy-proxy` running `lucaslorentz/caddy-docker-proxy` (pin a real tag), with `CADDY_INGRESS_NETWORKS=docksy` and ports 80/443. TLS is automatic.
- **App containers:**
  - name: `dx-<appName>-<deploy8>`
  - labels: `docksy.managed=true`, `docksy.app=<appId>`, `docksy.deployment=<deploymentId>`
  - routed apps also get `caddy=<domain1>, <domain2>` and `caddy.reverse_proxy={{upstreams <port>}}`
- **Default domain:** `defaultDomain()` → `<app>.<ip>.sslip.io`.
- **Paths:**
  - `/var/lib/docksy/{builds,backups,volumes}`
  - `/etc/docksy/agent.env`
  - systemd unit `docksy-agent.service`
  - agent binary `/usr/local/bin/docksy-agent`
- **Scripts in `deploy/scripts/`** (owned by `devops`, run via `bash -s` over SSH with env vars):
  - `provision.sh`: idempotent. Installs Docker via get.docker.com if missing, creates the network, starts/updates docksy-proxy, creates dirs, optionally opens ufw 80/443. Prints `::step:: <text>` lines for UI progress.
  - `install-agent.sh`: needs `DOCKSY_URL`, `DOCKSY_AGENT_TOKEN`. Downloads `${DOCKSY_URL}/api/agent/v1/binary/linux-$(arch)`, falling back to the GitHub release `https://github.com/osmanyousaaf/docksy/releases/latest/download/docksy-agent-linux-<arch>`. Writes env, installs the systemd unit, then enables and starts it. Also prints `::step::` lines.

Mount routes **per route**: `app.get('/api/v1/...', requireUser, handler)`. **Do not** use `r.use(requireUser)` on a sub-router mounted at `/api/v1`, and do not use `app.use('/api/v1/*', requireUser)`. Both block every public route registered after them, including `/public/status`, webhooks, `/auth/*` and the agent endpoints. This was verified in Hono. A sub-router is fine only if every route on it passes `requireUser` explicitly.

Templates may need a container command: `templateCommand(templateId): string[] | null` is exported from `core/apps/templates.ts`. core-deploy appends it to `docker run`. core-deploy also adds `--network-alias <appName>`, so apps can reach databases by name (e.g. `postgres://…@my-db:5432`).

## 8. CLI + MCP

**Client (`@crovenai/docksy-client`).** `new DocksyClient({url, token})` with typed methods for every route in §4. Uses fetch; errors throw `DocksyApiError`; SSE is exposed via an async iterator.   - `docksy mcp` (runs the MCP server in-process)

**MCP server (`docksy-mcp`, stdio; also `--http` for streamable HTTP bound to 127.0.0.1).** Env `DOCKSY_URL`, `DOCKSY_TOKEN`; `DOCKSY_READONLY=1` hides write tools.

## 10. Packaging (`devops`)

- **Dockerfile:**
  - multi-stage: golang builds the agent for linux amd64+arm64
  - node:24 builds the web
  - runtime is `node:24-slim`, containing the server src, `packages/shared`, `web/dist`, `deploy/scripts` and `agent/bin`
  - `ENV NODE_ENV=production DOCKSY_DATA_DIR=/data`
  - exposes 8080, has a healthcheck, runs as non-root
- **`docker-compose.yml`:** the `docksy` service with a `/data` volume.
- **`install.sh`:** a one-line installer (`curl -fsSL https://raw.githubusercontent.com/osmanyousaaf/docksy/main/install.sh | sudo bash`). It:
  1. installs Docker
  2. generates `DOCKSY_SECRET`
  3. writes `/opt/docksy/.env` and compose
  4. starts Docksy
  5. registers the host itself as server "localhost" via SSH key (adds Docksy's public key to root's authorized_keys)
  6. prints the URL
  It must be idempotent and support `--uninstall`.
- **`.github/workflows`:**
  - `ci.yml`: typecheck, test, web build, go test, docker build
  - `release.yml`: on tag `v*`, push the multi-arch image to GHCR, attach agent binaries to the GitHub Release, publish the npm packages with provenance, Pages for `docs/`
  - CodeQL and Dependabot
- **`e2e/fake-vps/`:** a Dockerfile (Debian + sshd + Docker-in-Docker) that acts as a VPS locally, plus `e2e/run.sh`, which boots Docksy and the fake VPS, adds the server, provisions it, deploys a sample app (`e2e/sample-app` with a tiny Node server) and asserts that metrics arrive.
